# Pubblicare un APK QA aggiornato

L'utente desidera trovare un APK scaricabile dopo ogni modifica dell'app, nella [pagina Releases](https://github.com/Hellvisback/calendario-turni/releases). Ogni pubblicazione è una nuova pre-release con versione e `versionCode` crescenti. Il package QA `com.turni.calendario.setupqa` è separato dall'app personale. Non chiamare il pacchetto QA un aggiornamento dell'app personale.

La beta.18 (63) è stata compilata con `bash scripts/check-android.sh assembleBeta testDebugUnitTest -PsetupProbe`, lint vitale e 485 test superati. Firma QA SHA-256: `5b3da847037ec649a4c90b62af605ff234604eeb75cd15250ad8955ace599b9f`. Conservare privatamente la chiave QA del cloud: per aggiornare una precedente installazione QA Android richiede la stessa firma. La chiave originale dell'app personale è diversa e non si trova nel repository.

Per ogni nuova versione, incrementare `versionCode` e `versionName`, compilare e testare il package QA; verificare con `aapt` e `apksigner` package, versione e certificato, calcolare SHA-256 e pubblicare i sorgenti su `main`. `scripts/release.ps1 -PublishExistingArtifact` verifica questi valori, il commit sorgente e l'assenza di tag/release esistenti, quindi pubblica solo l'APK versionato. Usare `-VerifyOnly` prima della pubblicazione. Non sovrascrivere asset o tag esistenti.

Se l'upload diretto a `uploads.github.com` restituisce 401, si può usare il workflow manuale `.github/workflows/publish-qa.yml`: caricare l'APK come blob GitHub tramite API (senza aggiungerlo all'albero Git), verificare che il blob riscaricato abbia lo stesso SHA-256, quindi avviare il workflow su `main` con `blob_sha`, `apk_sha256`, `signer_sha256`, `source_commit`, `version_name` e `version_code`. Il workflow usa il token GitHub Actions con `contents: write`, recupera il blob, verifica nuovamente tutto ed esegue `scripts/release.ps1`. Attendere il successo, controllare che la release contenga il solo APK previsto e riscaricarlo per verificarne l'impronta. Non inserire chiavi, token o dati personali nel repository.

Esempio verificato: [beta.18 QA](https://github.com/Hellvisback/calendario-turni/releases/tag/v1.8.0-beta.18), APK SHA-256 `cbfbec9ee05fba90aea4d01d300111aba6126d04eb01c67fe2802064d8ec1fb5`, sorgenti `3e39aa75edfa1de7930877a1785b413881a51e0d`, workflow run `44070210782`. È una pre-release, pertanto il collegamento GitHub `/releases/latest` potrebbe indicare una versione stabile precedente.

Se il workflow è cambiato dopo il commit del codice e GitHub rifiuta il tag sul commit intermedio con 403, usare come SourceCommit il commit corrente del workflow solo dopo aver verificato che i file app e la versione corrispondano ancora al binario compilato. Nella beta.20 il codice app era identico fra `7dc4bae` e `8ff15be`; pubblicazione riuscita sul secondo senza modificare i byte APK né ampliare i permessi contents:write. Il workflow accetta note di rilascio specifiche tramite input `release_notes`.
